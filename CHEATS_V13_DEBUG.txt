GBARunner3 cheats v13 debug

Build-log diagnosis from v12:
  __bss_vma = 0x06820704 while VRAM A ends at 0x06820000.
  Overflow = 0x704 = 1796 bytes.

This is not primarily a BSS-state-size problem. __bss_vma is captured immediately
AFTER .text/.rodata/.data, so v12 moved too much executable CheatService code back
into the 128 KiB VRAM-A region.

v13 layout:
- CheatService.cpp: boot-critical loader/parser remains in VRAM A.
- CheatRuntime.cpp: post-boot UI, menu, VBlank executor and CodeBreaker execution
  move to EWRAM.
- CheatRuntime.o alone uses -mlong-calls.
- CheatService/BootDebug state remains in EWRAM BSS as before.
- Detailed loader checkpoints 52..65 remain available on the bottom screen.

Expected diagnostic value:
- If it stops at 52/53/54/etc, the loader is now definitely executing in VRAM A.
- If it reaches 65 and later stops at 44 before 45, the remaining issue is the
  EWRAM post-boot runtime entry (InitializeUi), isolated from the loader.

Additional size/range safeguards:
- BootDebug.o is compiled with -Os because it is diagnostic-only.
- InitializeUi() is declared long_call so main.cpp emits a range-safe call when
  the implementation resides in EWRAM.
